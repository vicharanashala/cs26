SECTION 1 — PROJECT CONCEPT & MISSION
================================================================================

Vicharanashala is an onboarding and learning ecosystem for internships. OAQ
(Once Asked Questions) is its core knowledge-sharing and query-tracking portal.

THE PROBLEM:
  Interns frequently encounter blocking technical or administrative issues.
  Without a structured knowledge base, the same questions are asked repeatedly,
  overwhelming mentors and slowing onboarding.

THE SOLUTION:
  A gamified, peer-to-peer query resolution system where interns are incentivized
  to help each other. Every question is asked and answered exactly once, then
  joins a searchable baseline knowledge base accessible to all future cohorts.

CORE TENETS:
  - Knowledge Persistence: Answers persist forever as searchable artifacts.
  - Zero Redundancy: Duplicate queries are detected and blocked before submission.
  - Gamified Engagement: Skill Points (SP), leaderboards, and badges drive
    participation.
  - Quality Assurance: Automated Yaksha-mini audits and community voting ensure
    answer quality.
  - Real-Time Collaboration: Socket.io broadcasts keep all sessions synchronized.

SECTION 2 — SYSTEM ARCHITECTURE OVERVIEW
================================================================================

The platform follows a three-tier MERN architecture with real-time capabilities:

PRESENTATION LAYER (CLIENT):
  - React 18 SPA with Vite bundler (dev server on port 5173)
  - React Router v6 for client-side navigation
  - Socket.io-client for real-time bidirectional events
  - Web Speech API for voice search and speech playback
  - Context API for state management (Toast, Theme, Socket, Auth)

APPLICATION LAYER (SERVER):
  - Node.js + Express REST API (port 5001)
  - Socket.io server for WebSocket broadcasting
  - Passport.js for JWT + Google OAuth2 authentication
  - Mongoose ODM for MongoDB interactions
  - OpenAI SDK for GPT-3.5-turbo RAG streaming (optional)
  - Background services: staleWatcher for stale query auto-escalation

DATA LAYER (DATABASE):
  - MongoDB Atlas cluster (replica set with 3 shards)
  - Collections: OAQIssue, User, Section, CoOccurrence, SPLedger, Thread
  - Indexing on queryText, email, issueId, createdAt for performance

HIGH-LEVEL DATA FLOW:
  Client (React SPA :5173) --HTTP/SSE--> Server (Express :5001)
    --Mongoose--> MongoDB Atlas
  Client (Socket.io) --WebSocket--> Server (Socket.io) --Broadcasts--> All clients
  Server --OpenAI API--> GPT-3.5-turbo (optional RAG streaming)

FEATURE 1 — 13 LOCKED ONBOARDING FAQ OAQ LIBRARY
----------------------------------------------------------------------
Core Feature Idea:
  An instantly accessible, read-only onboarding FAQ center representing 13
  static categories that prevents common administrative queries from cluttering
  the open resolver board.

How It Works:
  Users see 13 onboarding topic accordions (ViBe, NOC, Teams, Onboarding,
  Reports, Finance, Schedule, Lab, Eval, SP, Yaksha, Tracker, General).
  Clicking a category slides open the card to reveal the verified answer. Only
  one accordion is open at a time. Sorting supports ID, Most Upvoted, A->Z,
  Newest, or Oldest.

Pipeline / Data Flow:
  Client fetches baseline issues via GET /api/oaq/baseline
    -> Server queries OAQIssue where isBaseline=true
    -> Returns sorted accordion data
    -> Client renders accordion cards with single-open behavior.


FEATURE 2 — FIRST-COME, FIRST-SERVED (FCFS) RESOLVER BOARD
----------------------------------------------------------------------
Core Feature Idea:
  A gamified dynamic resolver board where interns compete to claim and resolve
  open technical roadblocks raised by peers.

How It Works:
  Lists all unresolved queries in a public table grid. The first intern to
  respond claims the FCFS resolution via a 30-second TTL lock. Concurrent
  attempts trigger a 409 collision alert. Submitted answers enter a pending
  state for community voting. Stale queries (no FCFS claimed within 24h) are
  highlighted in red/amber. An Activity Summary card shows each user their
  personal pulse: queries raised, FCFS wins, pending replies, and total
  upvotes.

Pipeline / Data Flow:
  User clicks Resolve -> Server sets lockedBy + lockExpiry (30s TTL) on
  OAQIssue -> Client submits answer -> Server validates via Yaksha-mini audit
  -> On pass, answer enters pending communityReplies -> Socket.io broadcasts
  issue:resolved-attempt -> Background staleWatcher runs every 10 minutes,
  marking queries >24h as stale with priority escalation.


FEATURE 3 — AUTOMATED CONTENT QUALITY AUDITOR (YAKSHA-MINI)
----------------------------------------------------------------------
Core Feature Idea:
  A real-time content gate protecting the knowledge base from keyboard mashing,
  spam, copy-paste blocks, and low-quality one-liners.

How It Works:
  Runs automatically on every resolution and reply submission before acceptance.
  Validates: minimum 20 characters, at least 3 words, no repetitive keyboard
  gibberish (e.g. "asdfasdf"), meaningful word ratio >40%. A real-time preview
  badge shows the quality score before the user submits. Failed submissions are
  rejected with a -20 SP penalty.

Pipeline / Data Flow:
  Client sends answer text -> Server runs validateAnswer() -> Checks: length
  >= 20, words >= 3, no keyboard_pattern match, meaningful_ratio > 0.40
  -> If fail: reject with 400, deduct 20 SP, log to SPLedger
  -> If pass: proceed to communityReplies submission.


FEATURE 4 — COMMUNITY AUTO-PROMOTION SYSTEM
----------------------------------------------------------------------
Core Feature Idea:
  Peer-driven validation of knowledge through collective community voting.

How It Works:
  When an intern submits an FCFS answer, it enters a pending review queue.
  Other interns upvote or downvote it. Once a reply accumulates 3 net upvotes,
  it is auto-promoted to "Resolved" and locked as the master answer. The
  resolver receives +50 SP. Voting is open to all authenticated interns.

Pipeline / Data Flow:
  Vote event -> Server calls checkAutoPromote() on the issue -> Checks if any
  communityReply has upvotes - downvotes >= 3 -> If yes: set status=Resolved,
  answer=promotedReply.text, resolvedBy=promotedReply.repliedBy, award +50 SP
  to resolver, broadcast issue:resolved via Socket.io.


FEATURE 5 — AUTO-ESCALATION THRESHOLD HOOK
----------------------------------------------------------------------
Core Feature Idea:
  Ensures high-severity roadblocks or broadly-interesting queries are
  automatically highlighted for mentor attention.

How It Works:
  The system tracks upvotes on unresolved resolver queries. If an open query
  reaches 5 upvotes within a 2-hour window, its priority is automatically
  elevated from Normal to HIGH, and a Socket.io alert is broadcast to all
  connected mentors.

Pipeline / Data Flow:
  Upvote on open issue -> Server checks upvoteCount >= 5 -> Checks if within
  2-hour window from createdAt -> If within window: set priority=HIGH, add +5
  SP to author, emit escalation event via Socket.io to mentor room.


FEATURE 6 — COLLABORATIVE RECOMMENDATION RAIL (PEOPLE ALSO ASKED)
----------------------------------------------------------------------
Core Feature Idea:
  Contextually related query suggestions based on collective browsing habits
  of the cohort.

How It Works:
  The system tracks co-occurrence pairs whenever a user views an issue detail
  page. Each view increments a co-occurrence counter for (currentIssue,
  viewedIssue). The top related questions are displayed alongside the active
  query as "People Also Asked" recommendations, sorted by co-occurrence count.

Pipeline / Data Flow:
  User views issue A -> Client sends POST /api/oaq/co-occurrence with
  {issueA, issueB} -> Server upserts CoOccurrence document, increments
  viewCount -> On issue detail load, server queries CoOccurrence for top
  entries related to current issue -> Returns sorted recommendations.


FEATURE 7 — RSS TRENDING FEED
----------------------------------------------------------------------
Core Feature Idea:
  A live feed of the cohort's most relevant resolved issues and trending
  announcements on the homepage.

How It Works:
  Displays the top 15 resolved issues across all categories, sorted by upvote
  count with pinned items first, then featured, then others. Auto-refreshes
  every 5 minutes via setInterval on the client.

Pipeline / Data Flow:
  Client setInterval(5000ms) -> GET /api/oaq/trending -> Server queries
  OAQIssue where status=Resolved, sorts by isPinned desc, isFeatured desc,
  upvoteCount desc, limits 15 -> Returns feed data -> Client renders card
  list with timeAgo timestamps.


FEATURE 8 — VOICE SEARCH & SPEECH PLAYBACK
----------------------------------------------------------------------
Core Feature Idea:
  Enhances accessibility with voice-controlled search and auditory answer
  playback using the Web Speech API.

How It Works:
  Users click a microphone icon to speak and search baseline FAQs. Speech
  recognition converts audio to text and triggers a search. Each FAQ entry has
  a speaker button that uses SpeechSynthesis to read the answer aloud in a
  natural en-IN accent voice.

Pipeline / Data Flow:
  Microphone click -> navigator.mediaDevices.getUserMedia ->
  SpeechRecognition.start() -> On result, transcript sent as search query
  -> Client filters baseline FAQs -> Speaker button click ->
  SpeechSynthesis.speak(utterance) with lang="en-IN", rate=0.9.


FEATURE 9 — GAMIFIED SKILL POINTS (SP) & WALLET SUBSYSTEM
----------------------------------------------------------------------
Core Feature Idea:
  Motivate interns with gamified metrics, progress visualizers, and milestones
  through a comprehensive wallet system.

How It Works:
  - Overview Tab: Animates the user's total SP on load with a counting-up
    animation.
  - Ledger Tab: Full credit/debit transaction history showing every SP change
    with reason and timestamp.
  - Leaderboard Tab: Dynamic bar chart comparing all intern balances relative
    to the highest earner, plus a top-50 ranked list with "Your Rank"
    highlight.
  - SP Awards Modal (Admin/Superadmin): When closing a thread, opens a modal
    to award custom SP to a selected participant from a dropdown of thread
    contributors.
  - Confetti Celebrations: canvas-confetti fires at SP milestones (100, 250,
    500, 1000).

SP Rules:
  Action                                    SP Change
  ----------------------------------------+-----------
  Submit a valid FCFS reply               |   +5 SP
  Win FCFS resolution (auto-promoted)     |  +50 SP
  Raise a unique query                    |  +10 SP
  Auto-escalation trigger                 |   +5 SP
  Fail Yaksha audit                       |  -20 SP
  Thread close award (Admin)              |  Custom

Pipeline / Data Flow:
  Any SP-affecting action -> Server creates SPLedger document with userId,
  delta, reason, refId, createdAt -> Updates User.sp with $inc -> Socket.io
  broadcasts wallet:update to affected user -> Client SP counter animates on
  next load.


FEATURE 10 — COLLABORATIVE NESTED THREAD DISCUSSIONS
----------------------------------------------------------------------
Core Feature Idea:
  A nested discussion forum for complex, deep-dive technical conversations
  extending beyond standard Q&A.

How It Works:
  - Nested Tree Layout: Replies render in indented conversation trees with
    vertical connecting lines.
  - OP Tags: Thread creator labeled with "OP" badge.
  - Upvote/Downvote: Users can vote on any reply; net vote count displayed.
  - Reply Inline: Reply directly below any message in the nested tree.
  - Thread Lock/Unlock (Mentor+): Locks halt all incoming replies.
  - Mark Resolved (OP or Mentor+): Conceptual satisfaction marker; no SP.
  - Best Reply Promotion (Mentor+): Accepts reply as best answer, auto-marks
    thread resolved, highlights as "Accepted."
  - Dynamic SP Award (Admin/Superadmin): When closing a thread, awards custom
    SP to a selected participant.

Pipeline / Data Flow:
  CRUD via /api/threads -> Server manages nested communityReplies with
  repliedTo references for parent-child tree traversal -> Client renders
  recursive tree component with connecting lines -> Lock/unlock toggles
  isLocked boolean -> Best reply sets resolvedAnswerId and isResolved=true.


FEATURE 11 — DYNAMIC SECTION FILTERS
----------------------------------------------------------------------
Core Feature Idea:
  Multi-select filter bar that simultaneously filters across baseline,
  trending, and tracker views.

How It Works:
  Users select one or more section categories from a filter bar on the
  homepage. Selected category predicates are fed into API calls, applying
  filters to OAQ Library, Trending Feed, and Resolver Board views
  simultaneously.

Pipeline / Data Flow:
  User selects section tags -> Client updates filteredSections state ->
  Appends ?sections=01,02,03 to all API GET requests -> Server parses
  categoryTag $in filter in Mongoose queries -> Returns filtered results.


FEATURE 12 — ADMIN MODERATION & MANAGEMENT PANEL
----------------------------------------------------------------------
Core Feature Idea:
  A consolidated administrative dashboard for organizing categories, managing
  rosters, and reviewing flagged content.

How It Works:
  - Mod Queues: Distinct queues for flagged replies, downvoted issues, and
    unanswered queries.
  - Roster Edits: Modify cohort profiles and SP balances. Role assignments are
    protected (no self-role-change, only Superadmin assigns Admin/Superadmin).
  - Dynamic Sections: Full CRUD over category lists.
  - Seeder Gates: Master seeder triggers to clear and re-initialize baseline

  - Issue Detail View: Dedicated page for each issue with full history,
    replies, voting, and moderation actions.

Pipeline / Data Flow:
  Admin routes under /api/admin with role middleware -> Mod queues query
  OAQIssue/Thread with flags -> Roster edits update User model -> Section
  CRUD on Section model -> Seeder triggers /api/admin/seed with superadmin
  guard.


FEATURE 13 — REAL-TIME SYNC BROADCASTER
----------------------------------------------------------------------
Core Feature Idea:
  Instant synchronization across all online sessions without manual refreshes.

How It Works:
  Socket.io broadcasts on every meaningful action: issue created, resolved,
  upvoted, replied, escalated, thread locked/unlocked, duplicate marked.
  Toast notifications appear for all connected users. Socket reconnection UI
  shows an amber "Reconnecting..." banner when connection drops.

Pipeline / Data Flow:
  Server action occurs -> io.emit(eventName, payload) -> Client socket
  listeners handle each event type -> Toast displayed via ToastContext ->
  Relevant UI component re-renders -> On disconnect, SocketContext sets
  connected=false, Topbar shows reconnection banner.


FEATURE 14 — DUPLICATE QUERY PREVENTION
----------------------------------------------------------------------
Core Feature Idea:
  Prevents redundant queries before they are raised by detecting similarity
  against existing issues.

How It Works:
  As the user types in the Raise Query modal, a dual-algorithm similarity
  scorer runs in the background: word-level matching (50% weight) + character
  overlap scoring (50% weight) against all non-Duplicate issues including
  baseline FAQs. Results above a 35% threshold display in a color-coded
  warning panel: red for >=70%, amber for >=50%, green for <50%. Each result
  shows match percentage, section tag, FAQ badge, and status. Uses 400ms
  debounce.

Pipeline / Data Flow:
  User types queryText -> 400ms debounce -> POST /api/oaq/check-duplicate
  -> Server iterates all non-duplicate issues + baselines -> Computes
  word-level Jaccard similarity (50%) + character bigram overlap (50%)
  -> Composite score >= 35% returned as warnings -> Client renders color-coded
  warning panel -> User can cancel submission and view existing answer.


FEATURE 15 — YAKSHA MINI AI CHAT WIDGET
----------------------------------------------------------------------
Core Feature Idea:
  An always-accessible AI assistant backed by the FAQ knowledge base with
  real-time streaming responses.

How It Works:
  A floating chatbot button in the bottom-right corner opens a chat panel.
  Messages are sent to POST /api/rag/chat. The server builds context by
  retrieving relevant resolved baseline Q&As via MongoDB $regex text search.
  If OPENAI_API_KEY is configured, responses stream from GPT-3.5-turbo via
  Server-Sent Events (SSE); otherwise a fallback returns keyword-matched KB
  answers as plain text. Widget visible only to authenticated users. Chat
  history resets each session. Enter sends, Shift+Enter adds newline. Blinking
  cursor shown during streaming.

Pipeline / Data Flow:
  User sends message -> POST /api/rag/chat -> Server searches KB via $regex
  on queryText/answer -> If OPENAI_API_KEY set: build context prompt + query,
  fetch streaming from OpenAI API, pipe SSE chunks via res.write() -> Client
  reads SSE stream, appends tokens to message bubble with blinking cursor
  -> If no API key: return top KB match as plain text response.

SECTION 9 — DEPLOYMENT PIPELINE
================================================================================

DEVELOPMENT ENVIRONMENT:
  - Server: Node.js on port 5001 with nodemon for hot-reload
  - Client: Vite dev server on port 5173 with HMR
  - Database: MongoDB Atlas cluster (shared M7 replica set)
  - Environment: .env files for both server/ and client/

GIT WORKFLOW:
  1. Feature branches from main (git checkout -b <name>)
  2. Pull requests with descriptive titles
  3. Merge to main after review + conflict resolution
  4. git push origin main to deploy

BUILD & DEPLOY:
  1. Client: vite build produces static dist/ folder
  2. Server: Node.js Express serves API + optionally serves dist/ as static
  3. Environment variables configured per target
  4. MongoDB connection string points to Atlas replica set with SSL

ENVIRONMENT VARIABLES:
  Variable               Purpose                      Required
  ---------------------  -------------------------   --------
  PORT                   Server listen port           Yes (default 5000)
  MONGO_URI              MongoDB Atlas connection     Yes
  JWT_SECRET             Token signing secret         Yes
  CLIENT_ORIGIN          CORS allowed origin          Yes
  OPENAI_API_KEY         GPT-3.5-turbo streaming     Optional
